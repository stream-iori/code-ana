## 3. 实施默认建议及其边界

| 事项 | 本方案建议 | 证据 / 决定方式 |
|---|---|---|
| worker IPC | 专用继承管道 + 长度前缀 protobuf；stdout/stderr 只作日志 | contracts 建议；P0-06 验证取消、背压与中断 |
| daemon 承载 | loopback 动态端口 + 用户运行目录注册；必须校验所属用户 | runtime 建议；P0-06 固定访问校验方式与权限，不能只凭端口已知授权 |
| daemon 升级 | 首版显式 drain/restart，不自动终止不兼容服务 | 最小生命周期实现；用户无需为此再次选择协议 |
| 存储 | SQLite generation 作为 P0 首测方案 | 复制/RSS/磁盘/恢复实测不合适时再评估 live WAL，不预先切换 |
| 增量 | 冷基线先使用足够摘要和事实，热复用放 P2 | 降低漏依赖风险；全量为对照 |
| 工程拆分 | 需要时建立 model/config/application/query/storage；Java 按 core/framework/bridge 拆分 | 不为每个模块提前建立空进程或空 crate |
| 目标产物证明 | 版本化 BuildArtifactManifest 与 BuildContext；来源未知则 coverage 缺口/拒绝 | D09 要求可验证，但 docs 尚未给出具体格式；P0-03 完成候选规范 |
| 人工标注历史 | 正文版本与绑定状态保全，当前阶段不额外开放完整正文历史回溯操作 | docs 将其留作 D10；保留以后扩展的数据边界，不阻塞当前主线 |
| 平台能力 | macOS 先按实际架构验收，其他架构明确 unsupported | S01；不存在未经运行验证的跨架构承诺 |

这些是可执行的候选选择，不是新增用户确认。原型结论形成后更新设计文档，再作为实现基线。

## 4. 需要技术证据解决的问题

| 问题 | 原型需要回答 | 失败后的动作 |
|---|---|---|
| 原生库能否承接 javac 完整链路？ | 实际共享库启动目标 JDK 桥、独立模型/ASM/框架、取消/资源回收；分开验证桥字节码与 adapter Java 25 | 修可达性或调整 javac 执行边界；若动摇 D13，形成具体证据后提请决策；不退其他解析器 |
| Rust 派发需要哪些 Java 事实？ | 重载/接口/继承/default 方法/外部类型缺口下的候选与 proof | 补 facet；仍无法表达则重新评审 D06 |
| 冷基线是否充分？ | 编译器上下文丢弃后，封存源码能否提供 javac 类型输入，BaselineFacts 能否支撑失败查找/Bean/XML 消费者闭包 | 扩基线或终止 attempt 重规划；不能悄悄读取 live workspace |
| Maven 如何避免模型误判？ | 父子模块/profile/属性/依赖顺序能否从已有有效模型证明 | 明确受支持范围；要求外部导出模型/产物，不执行 Maven 补齐 |
| 产物与输入的“证明”有多强？ | 摘要清单如何生成、来源如何记录、是否只证明对应声明而非重现构建 | 公开可信程度；无法核验不视为 fully verified，不以 mtime 代替 |
| 工具链如何固定？ | 分析所需 JDK 文件集合/摘要与捕获方式，预算成本 | 缩到实际依赖集合；无法固定则能力缺口或拒绝可信发布 |
| 文件持久化在 macOS 是否成立？ | SQLite backup/sidecar、同文件系统移动、文件/目录同步、提交窗口 | 修发布顺序；只记录实际验证的故障范围 |
| 门禁默认政策是什么？ | 哪些诊断/缺口允许 partial 发布、哪些必须拒绝，strict 如何影响 | P0-07 固定有限政策与原因码；门禁与原始质量独立 |
| 所有语言都关闭后怎样清理 head？ | docs 同时要求无启用语言拒绝 index、关闭分区清理 | 当前按显式启用规则拒绝新语义索引，保留已发布身份/历史；不要伪装为新空 revision。若需清空入口，另定义显式操作 |
| text_only 和捕获范围如何解释？ | 设计建议 text_only 不进入语义/捕获/diff，与 search.text.include 独立 | P0-03 冻结规则和示例，必需控制输入被排除仍拒绝 |
| 缺省容量与超限策略是多少？ | 每进程 RSS、全局预约、流/队列/结果/GC 空间是否有界 | 用测量定参数；超限失败保旧版，不以“省略”为无限 |

### 本次明确的实施草案

| 事项 | 草案与边界 |
|---|---|
| 配置 | javac 固定，无 parser 切换；auto 只从用户登记项选唯一匹配 JDK，vm_classpath=false 拒绝；不猜 JAVA_HOME/PATH |
| 支持范围 | 先评估 Java 8/17/25 与同版本 Maven reactor，实际通过才列能力；混合版本/多个命名 JPMS 模块不提前承诺 |
| Lombok | 草案使用 off/model；独立声明 overlay，无处理器执行和 compile 开关；无旧配置兼容负担 |
| 发现 | 消费已有有效模型 metadata；不移植参考项目 Maven 扩展启动路径 |
| 优化 | P0/P1 串行、足够源码上下文；签名缓存/热复用/并行放 P2，缺缓存退源码不退解析器 |
| 测量 | 整个 worker 进程树预算，模型解码/编码/磁盘分别有界；不照搬参考项目默认值和性能门槛 |

以上具体实现仍需原型记录；D16 的后端选择已经确定，不列为待选择问题。
